# Epic 4 Context: 交易订单与评价（orders）

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让买家从商品详情页进入订单确认并创建「待支付」订单，通过模拟支付推进到「已支付/待交付」，此时才看到卖家 QQ/微信与认证状态，当面交付后确认收货、双方互评；交付前如货不对板可发起退款请求转入纠纷。本史诗把「下单 → 支付 → 交付 → 确认 → 评价」这段交易主干跑通，是整个平台存在的理由所在；它也是全系统一致性风险最高的地方——订单状态必须只能沿合法路径前进，否则会被人为跳过支付或收货后再退款，因此状态机是这一史诗的核心资产，而非附属逻辑。

## Stories

- Story 4.1: 下单创建订单
- Story 4.2: 模拟支付
- Story 4.3: 下单后展示联系方式
- Story 4.4: 订单状态机
- Story 4.5: 订单列表
- Story 4.6: 确认收货
- Story 4.7: 互评
- Story 4.8: 退款请求

## Requirements & Constraints

- 下单：已登录买家在已上架商品详情页点「立即购买」进入订单确认页（商品、价格、可选留言），确认后创建订单，初始状态「待支付」；留言可留空。
- 模拟支付：仅作状态流转，不接任何真实第三方支付网关；须在单个数据库事务内原子完成「待支付 → 已支付/待交付」。
- 状态合法性：只允许沿正常路径（待支付 → 已支付/待交付 → 已确认收货 → 已完成 → 已互评）与退款分支（已支付/待交付 → 纠纷 → 退款成功／退款失败）流转；任何非法跳转（如待支付直接确认收货、已确认收货再退款）必须被拒绝，而不是静默忽略或降级为提示。
- 联系方式隐私：下单前与「待支付」阶段绝不暴露卖家 QQ/微信；「已支付/待交付」及之后才展示 QQ/微信 + 认证状态。学号任何情况下不对外展示。
- 确认收货：仅「已支付/待交付」可执行，执行后订单进入「已确认收货」并由系统随即自动标记「已完成」，退款入口随之不可用。
- 互评：仅「已完成」可提交评价；买卖双方各自提交，双方均提交后订单才变「已互评」，单方提交不改变订单状态。
- 退款请求：仅「已支付/待交付」可发起且必须填写原因，提交后进入「纠纷」等待管理员裁决；「待支付」「已确认收货」（已转「已完成」）均不可发起。
- 订单列表：买家看「我的订单」、卖家看「售出订单」，展示每单当前状态与关键信息；只返回本人相关订单，他人订单不可见、不可通过改 URL 访问。
- 通用：所有写操作需登录鉴权；演示环境（Chrome/Edge）核心闭环无阻断。

## Technical Decisions

- **归属与分层**：全部落在 `orders` app（订单、支付、评价、退款）；分层单体 Django MTV，视图只做请求编排与鉴权，模板只渲染，业务规则下沉 Models/Services，下层禁止反向 import 上层。
- **状态机唯一定义点**：状态枚举（`choices`，取值为「待支付／已支付/待交付／已确认收货／已完成／已互评／纠纷／退款成功／退款失败」）与合法转移表只在 `orders` 的 models 层定义；每个合法转移封装为模型方法（`pay()` / `confirm_receipt()` / `request_refund()` / `resolve_refund()`），非法转移抛错拒绝。视图与模板**不得直接改 `status` 字段**；`dashboard` 的纠纷裁决调用 `resolve_refund()` 而非另写流转。
- **数据模型（ERD 约定）**：订单关联买家（User）与商品（Product）；评价与退款请求均挂在订单上，一个订单可产生多条评价（买卖双方各一条）与退款请求记录。评价人/被评人通过订单关系推导，不另建独立评分表。
- **字段约定**：价格 `DecimalField(10,2)`；状态用 `choices` 枚举；主键自增 int；时间 UTC（`USE_TZ=True`）；错误统一为表单错误。
- **事务**：模拟支付用 `transaction.atomic()` 包裹；状态机的「先校验当前状态、再迁移」在同一事务内完成，避免同一动作被重复提交两次而双重流转。
- **授权**：服务端强制（`login_required` + 查询按 `buyer`/`product__seller` 过滤）；买家/卖家身份由订单与商品关系判定，不依赖 `role` 字段；管理员专属动作不在本 app 暴露。
- **存储与栈**：Django ORM + migrations，开发/演示用 SQLite；命名遵循 app 复数小写、Model 单数 CamelCase（`Order`/`Review`/`RefundRequest`）、字段 snake_case、URL 语义命名（如 `/orders/<id>/`）。
- **集成面**：可下单对象只能是 `listings` 中 `status='approved'` 的商品；服务端渲染页面，无 SPA、无 WebSocket。

## UX & Interaction Patterns

- 买家主路径：商品详情页「立即购买」→ 订单确认页（商品、价格、留言可空）→ 创建订单（待支付）→「模拟支付」→ 支付成功即在同一页/详情页展现卖家 QQ/微信 + 认证标识 → 当面交付 →「确认收货」→ 评价。
- 状态即界面：订单列表与详情直接以当前状态呈现进度与可用动作；退款入口仅在「已支付/待交付」出现，确认收货后消失。
- 退款分支：在「已支付/待交付」提交退款请求 + 原因 → 订单显示「纠纷」等待裁决，此分支不再通向确认收货。
- 互评：双方在订单页各自提交评价，界面提示「等待对方评价」，双方齐备后订单显示「已互评」。
- 全部为 Bootstrap 服务端渲染桌面页面，仅 Chrome/Edge，无移动端、无实时推送。

## Cross-Story Dependencies

- 内部：4.4 定义的状态机与模型方法是 4.2／4.6／4.7／4.8 的共同底座，任何状态变更都必须走它；4.1 产出的「待支付」订单是 4.2 的前提；4.2 的「已支付/待交付」同时是 4.3 展示联系方式、4.6 确认收货、4.8 退款请求的前提；4.6 的「已完成」是 4.7 互评的前提；4.5 只读取上述故事产生的订单，自身不改变状态。
- 依赖 Epic 1：登录会话与买家/卖家身份；卖家 QQ/微信字段与 `is_verified` 认证位由 `accounts` 提供，4.3 仅按订单状态决定是否渲染。
- 依赖 Epic 2：仅已上架商品可下单，订单引用 `listings` 的商品；商品详情页的「立即购买」是 4.1 的入口。
- 依赖 Epic 5：4.8 产生的「纠纷」由管理员裁决（同意 →「退款成功」、不同意 →「退款失败」），裁决动作调用本史诗的状态机方法；本史诗不实现裁决界面。
- 对外输出：订单与纠纷数据是管理员看板「成交数／纠纷数」的统计来源；「已互评」为交易闭环终点，供个人中心「我的评价」展示。
