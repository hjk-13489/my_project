# PRD：校园二手书/闲置物品交易系统

## 0. 文档目的

本 PRD 面向开发此系统的团队（及课程评审），描述福州大学旗山校区**网页端二手交易平台**要做成什么样、给谁用、有哪些功能与约束。它基于已定稿的《Product Brief：校园二手书/闲置物品交易系统》（`_bmad-output/planning-artifacts/briefs/`）构建，并细化了 brief 中未展开的交互细节（发布审核时机、联系时机、站内聊天、订单状态机、退款纠纷流程）。

阅读约定：**术语以第 3 节术语表为准**，全文不再引入同义替换词；**功能需求（FR）全局编号**（FR-1、FR-2…），每条带可测的验收结果；**非功能需求（NFR）在第 5 节**，全部可量化/可验收；我推断而未与你确认之处用 `[ASSUMPTION]` 内联标注，并汇总在第 10 节假设索引。

## 1. 愿景

旗山校区的学生要买卖二手书和闲置物品，现状两条路都不好走：QQ 群信息零散、良莠不齐、数量少、翻找费力；闲鱼等功能虽全却不是为校园内交易设计，还带着物流、陌生交易这些「同校当面」场景里本不必要的负担。

本系统做一个**面向旗山校区学生的网页端二手交易平台**，用「同校身份」解决信任、用「当面交付」省掉物流，让学生顺畅走完「发布 → 审核 → 浏览/搜索 → 协商 → 下单 → 模拟支付 → 当面交付 → 确认收货 → 互评」的完整闭环。

它定位为一个**课堂作业**：尺度「不过度复杂、也不过于简陋」，交付一个可演示的系统加一份足够完整的文档。如果做好，可从旗山校区扩展到福大其他校区乃至更多高校，在开学季、毕业季形成专场效应。

## 2. 目标用户

### 2.1 要完成的工作（JTBD）

- **卖家（学生）**：把旧书、闲置物品变现或腾地方——需要一个能让东西被同校学生看到、且有人可信地来买的地方。
- **买家（学生）**：低价买到教材、日用品——需要一个能搜、能比、能放心「同校当面」交易的地方。
- **平台管理员**：维护平台秩序——审核/下架违规发布、处理交易纠纷、管理用户、查看数据看板。

### 2.2 非目标用户（v1）

- 校外用户（非旗山校区学生）。
- 商家 / 批量二手贩子。
- 需要物流快递的跨校、异地交易。

### 2.3 关键用户旅程

- **UJ-1. 陈晓发布闲置并通过审核。**
  - **Persona + context：** 陈晓，大二，想把上学期的教材和一台用旧的台灯卖掉。
  - **Entry state：** 已注册并登录、账号已认证；网页端。
  - **Path：** 打开「发布闲置」→ 填标题、描述、价格、成色，选分类，传图片 → 提交 → 商品进入「待审核」→ 收到审核结果通知。
  - **Climax：** 审核通过，商品「上架」，可在列表/搜索中被看到。
  - **Resolution：** 上架后等待买家联系或下单。
  - **Edge case：** 审核驳回 → 陈晓在「我的消息」看到驳回理由，修改后重新提交。

- **UJ-2. 林哲搜索、协商并下单。**
  - **Persona + context：** 林哲，大三，想低价买下学期的教材。
  - **Entry state：** 已登录、已认证；从首页/搜索进入。
  - **Path：** 搜关键词或按分类/价格/成色筛选 → 打开商品详情页 → 点「联系卖家」发站内消息协商 → 谈妥后点「立即购买」→ 订单确认页（商品、价格、留言）→ 点「模拟支付」。
  - **Climax：** 支付成功，订单进入「已支付/待交付」，此时展示卖家 QQ/微信 + 身份认证状态。
  - **Resolution：** 加卖家 QQ/微信，私下约定见面时间地点。
  - **Edge case：** 协商未成 → 不创建订单。

- **UJ-3. 林哲确认收货并互评（含退款分支）。**
  - **Persona + context：** 林哲（续 UJ-2），已支付、拿到货。
  - **Entry state：** 订单「已支付/待交付」。
  - **Path：** 当面拿到货 → 点「确认收货」→ 订单进入「已确认收货」并转入评价 → 双方提交评价。
  - **Climax：** 互评完成，订单「已互评」，闭环结束。
  - **Resolution：** 双方信用可被后续交易参考。
  - **Edge case：** 若在「已支付/待交付」阶段发现货不对板/质量问题，林哲发起退款请求（进入 UJ-4 纠纷），订单转入退款流程，**不再**进入确认收货。

- **UJ-4. 管理员处理审核与纠纷。**
  - **Persona + context：** 平台管理员，维护秩序。
  - **Entry state：** 登录后台。
  - **Path：** 待审核区查看商品（信息/图片/价格）→ 通过（上架）或驳回（填理由通知卖家）；对已上架违规商品点「下架」；纠纷区审核退款原因 → 同意退款或不同意。
  - **Climax：** 裁决生效：商品上架/下架，或订单状态变「退款成功 / 退款失败」。
  - **Resolution：** 相关用户收到通知。

## 3. 术语表

- **发布**：卖家创建一条闲置商品记录（填写字段 + 传图）。
- **待审核**：商品提交后、管理员审核前的状态，此状态下商品**不对外可见**。
- **上架**：商品经管理员审核通过后对外可见的状态。
- **下架**：商品被移出对外可见（违规商品由管理员执行）。
- **下单**：买家对某商品发起交易，创建订单。
- **模拟支付**：不接真实第三方支付的占位支付动作，成功后订单进入「已支付/待交付」。
- **确认收货**：买家在当面交付后点击，使订单进入「已确认收货」并转入评价。
- **互评**：买卖双方对本次交易互相评价，完成后订单为「已互评」。
- **退款请求**：买家在「已支付/待交付」阶段就货不对板/质量问题发起的申请。
- **纠纷**：退款请求产生后、管理员裁决前的状态。
- **退款成功 / 退款失败**：管理员裁决后的订单终态。
- **学号认证**：用户提交学号等校园身份信息、管理员核实通过后，账号标记为「已认证」。
- **成色**：商品的成新程度字段（预设取值集合）。
- **站内消息 / 我的消息**：系统内买卖双方与系统的通知/聊天入口。

## 4. 功能需求

### 4.1 用户账号与身份认证

**Description:** 学生注册登录，并通过学号认证获得「同校」可信身份。认证状态在商品详情页与下单后的联系方式处展示（实现 UJ-1 入口、支撑「同校可信」）。

#### FR-1: 注册

学生可用**学号 + 密码 + 昵称**注册账号；注册后账号状态为「待认证」。

**Consequences (testable):**
- 学号全局唯一，重复学号注册被拒绝并提示。
- 密码长度 ≥ 6 位。
- 注册成功后账号状态显示「待认证」。

#### FR-2: 登录 / 登出

已注册用户用学号 + 密码登录；可登出。

**Consequences (testable):**
- 正确凭据登录成功；错误凭据提示「学号或密码错误」。
- 未登录访问需登录的页面/操作时，跳转登录页。

#### FR-3: 学号身份认证

用户提交学号等校园身份信息，管理员核实通过后账号标记为「已认证」。

**Consequences (testable):**
- 「已认证」标识在商品详情页、以及下单后展示的联系方式旁可见。
- 「待认证」账号不显示「已认证」标识。
- 管理员可对「待认证」账号执行「通过/驳回」核实（见 FR-28）。

#### FR-4: 个人中心

登录用户可访问个人中心，查看**我的发布、我的订单、我的消息、我的评价**。

**Consequences (testable):**
- 各入口只显示当前登录用户自己的数据。

### 4.2 发布闲置

**Description:** 卖家发布闲置，经管理员审核后上架（实现 UJ-1）。`[ASSUMPTION: 发布需账号已认证才可提交]`

#### FR-5: 发布商品

已登录卖家填写**标题、描述、价格、成色、分类**并上传**图片**后提交。

**Consequences (testable):**
- 标题、描述、价格、成色、分类为必填，缺一不可提交。
- 价格为数字且 > 0，非法输入被拒绝。
- 分类从预设集合（教材 / 日用品 / 电子数码 / 其他）中选择。
- 图片可上传（≥ 1 张）。

#### FR-6: 待审核与上架

商品提交后进入「待审核」，**审核通过才上架**；待审核/驳回状态不对外可见。

**Consequences (testable):**
- 提交后商品状态为「待审核」，普通用户搜索/浏览不到该商品。
- 管理员审核通过后，商品状态变「上架」，可被搜索/浏览到。

#### FR-7: 驳回通知与重新提交

审核驳回时，卖家在「我的消息」收到**驳回理由**，可修改后重新提交。

**Consequences (testable):**
- 驳回理由出现在卖家「我的消息」中。
- 卖家可基于被驳回商品修改并重新提交，重新进入「待审核」。

#### FR-8: 查看我的发布

卖家可查看自己的发布列表及各商品当前状态。

**Consequences (testable):**
- 列表展示每件商品的当前状态（待审核 / 已上架 / 已下架）。

### 4.3 浏览与搜索

**Description:** 买家浏览、搜索、筛选商品，查看详情（实现 UJ-2 前半）。

#### FR-9: 商品列表浏览

已上架商品以列表形式展示（缩略图、标题、价格、成色）。

**Consequences (testable):**
- 列表只包含「上架」状态的商品。

#### FR-10: 关键词搜索

买家可按关键词搜索商品。

**Consequences (testable):**
- 关键词匹配商品**标题或描述**，返回命中商品。

#### FR-11: 分类 / 价格 / 成色筛选

买家可按**分类、价格区间、成色**筛选。

**Consequences (testable):**
- 分类、价格区间、成色筛选条件可组合，结果仅含满足全部条件的商品。

#### FR-12: 商品详情页

商品详情页展示全部图片、描述、价格、成色、分类、卖家昵称 + 认证状态，并提供「联系卖家」「立即购买」按钮。

**Consequences (testable):**
- 详情页展示全部字段与图片。
- 「联系卖家」进入站内聊天（FR-13）；「立即购买」进入下单（FR-17）。
- 展示卖家「已认证」标识（FR-3）。

### 4.4 站内聊天

**Description:** 买卖双方在系统内用文字协商（实现 UJ-2 协商环节）。为简化版：纯文字、轮询刷新，非实时推送。`[ASSUMPTION: 聊天仅下单前可用作协商，下单后联系转 QQ/微信；此处不限制聊天功能的技术形态]`

#### FR-13: 买家发起聊天

买家在商品详情页点「联系卖家」进入聊天窗口，可发送文字消息。

**Consequences (testable):**
- 买家可在**下单前**对卖家发送文字消息。
- 消息与对应商品、对应卖家关联。

#### FR-14: 卖家查看与回复

卖家在「我的消息」查看并回复买家消息。

**Consequences (testable):**
- 卖家「我的消息」列出收到的对话，可回复。
- 消息内容仅文字，不支持图片（FR-15）。

#### FR-15: 纯文字 + 轮询刷新

聊天仅支持**纯文字**；消息通过**刷新/轮询**更新，不做实时推送。

**Consequences (testable):**
- 发送/粘贴图片或富文本被拒绝或按纯文本处理。
- 新消息在页面刷新或轮询周期后可见（不要求 WebSocket 实时到达）。

#### FR-16: 未读提示

未读消息有数量提示。

**Consequences (testable):**
- 有新消息时「我的消息」入口显示未读数；查看后未读数清零。

### 4.5 交易与订单

**Description:** 买家下单、模拟支付，下单后展示卖家联系方式；订单按状态机流转（实现 UJ-2 后半）。

#### FR-17: 下单

买家点「立即购买」进入订单确认页（商品、价格、留言/备注），确认后创建订单，状态「待支付」。

**Consequences (testable):**
- 订单创建后状态为「待支付」。
- 留言/备注可选，可为空。

#### FR-18: 模拟支付

买家点「模拟支付」，订单进入「已支付/待交付」。

**Consequences (testable):**
- 支付成功后订单状态变「已支付/待交付」。
- 不调用真实第三方支付，仅做状态流转。

#### FR-19: 下单后展示联系方式

**下单成功后**，向买家展示卖家的 QQ/微信 + 身份认证状态。

**Consequences (testable):**
- 「待支付」「下单前」不展示卖家 QQ/微信。
- 「已支付/待交付」及之后的订单页/详情页展示卖家 QQ/微信 + 认证状态。

#### FR-20: 订单状态机

订单状态按状态机流转：

- **正常路径**：待支付 → 已支付/待交付 → 已确认收货 → 已完成 → 已互评
- **退款分支**：已支付/待交付 → [退款请求 → 纠纷] → 退款成功 / 退款失败

**Consequences (testable):**
- 订单只允许沿上述状态合法流转，非法跳转（如跳过支付直接确认收货）被拒绝。
- 确认收货后订单进入「已确认收货」并转入评价，不可再发起退款（FR-22、FR-24）。

#### FR-21: 订单列表

买家可查看「我的订单」，卖家可查看「售出订单」。

**Consequences (testable):**
- 订单列表展示各订单当前状态与关键信息。

### 4.6 交付、评价与退款

**Description:** 当面交付后确认收货、互评；以及交付前的退款请求（实现 UJ-3）。

#### FR-22: 确认收货

买家当面拿到货后点「确认收货」，订单进入「已确认收货」并转入评价，**不可再退款**。

**Consequences (testable):**
- 确认收货后订单状态为「已确认收货」，退款入口不可用。
- 订单随即标记「已完成」，开放双方互评。`[ASSUMPTION: 「已完成」由系统在确认收货后自动标记]`

#### FR-23: 互评

买卖双方对本次交易互相评价，双方提交后订单状态「已互评」。

**Consequences (testable):**
- 评价提交后订单状态变「已互评」。
- 双方均提交评价即视为闭环完成。

#### FR-24: 退款请求

买家在**「已支付/待交付」**阶段，就货不对板/质量问题提交退款请求 + 原因，订单进入「纠纷」。

**Consequences (testable):**
- 仅「已支付/待交付」状态可发起退款请求；「待支付」「已确认收货」不可发起。
- 提交后订单进入「纠纷」状态，等待管理员裁决。

### 4.7 管理员后台

**Description:** 管理员审核/下架、处理纠纷、管理用户、查看看板（实现 UJ-4）。

#### FR-25: 待审核区

管理员在「待审核区」查看待审核商品（信息/图片/价格），执行**通过（上架）**或**驳回（填理由）**。

**Consequences (testable):**
- 通过 → 商品上架（FR-6）。
- 驳回 → 填写的理由通知到卖家「我的消息」（FR-7）。

#### FR-26: 下架违规商品

管理员对已上架的违规商品点「下架」，卖家收到「商品违规已下架」通知。

**Consequences (testable):**
- 下架后商品不再对外可见。
- 卖家「我的消息」收到「商品违规已下架」通知。

#### FR-27: 纠纷裁决

管理员查看退款请求与原因，裁决**同意退款**或**不同意**；裁决后订单状态变「退款成功」或「退款失败」。

**Consequences (testable):**
- 同意退款 → 订单「退款成功」；不同意 → 订单「退款失败」。
- 裁决结果通知到相关用户。

#### FR-28: 用户管理

管理员可查看用户、**核实认证用户**、**封禁违规用户**。

**Consequences (testable):**
- 核实通过 → 账号标记「已认证」（FR-3）。
- 封禁 → 该账号无法登录或无法发布。`[ASSUMPTION: 封禁后果为「无法登录/发布」]`

#### FR-29: 数据看板

管理员可查看**用户数、发布数、成交数、纠纷数**等统计。

**Consequences (testable):**
- 看板展示上述至少四个统计指标，且数值与后台数据一致。

## 5. 非功能需求（NFR，跨切面、可测）

#### NFR-1（性能）

商品列表/搜索接口响应时间 **≤ 1 秒**（P95，课堂演示环境）；普通页面首屏加载 **≤ 2 秒**。

#### NFR-2（安全）

- 密码不以明文存储（哈希 + 加盐）。
- 所有写操作（发布、下单、评价、聊天、审核等）需登录鉴权；未登录请求被拒绝。
- 用户只能访问/操作本人数据（订单、消息、评价），越权访问被拒绝。

#### NFR-3（数据一致性）

订单状态只允许沿状态机（FR-20）合法流转，非法跳转被拒绝；「待审核」商品不可被搜索/浏览到。

#### NFR-4（隐私）

卖家 QQ/微信仅对**已下单**的买家展示（FR-19）；学号不在公开页面展示，仅管理员可见。

#### NFR-5（兼容性）

在最新版 Chrome、Edge 上功能完整可用。

#### NFR-6（可用性）

演示全程，核心闭环（发布→审核→浏览→下单→支付→交付→确认→评价）无阻断性故障。

## 6. 明确不做（Non-Goals）

- **不做真实第三方支付**（用模拟支付，跑通订单状态流转即可）。
- **不做物流/快递**（同校当面交付）。
- **不做完整即时通讯**：站内聊天为简化版，**不支持图片、不做实时推送**（轮询刷新）。
- **不做校外 / 跨校区交易**（v1 仅旗山校区）。
- **不做移动端 App**（v1 仅网页端）。

## 7. MVP 范围

### 7.1 包含

- 注册登录 + 学号/校园身份认证。
- 发布闲置（标题、描述、价格、图片、成色、分类）+ 先审后上架。
- 浏览 + 搜索/筛选（关键词、分类、价格、成色）。
- 站内聊天（纯文字、轮询）。
- 下单 + 模拟支付 + 订单状态机（含退款分支）。
- 下单后展示卖家联系方式 + 认证状态。
- 确认收货 + 互评。
- 退款请求与管理员裁决。
- 管理员后台（审核/下架、纠纷裁决、用户管理、数据看板）。

### 7.2 不包含（MVP）

- 真实第三方支付。
- 物流/快递。
- 站内图片/富文本聊天、实时推送。
- 移动端 App、跨校区。

## 8. 成功指标

**Primary**

- **SM-1（演示流畅）**：主流程「注册→发布→审核→浏览→下单→模拟支付→交付→确认收货→互评」在演示中一次走通、无卡壳。Validates FR-1~FR-29（核心闭环）。
- **SM-2（自助可用）**：一个用户不看帮助，5 分钟内走完「注册→发布一件闲置」和「浏览→下单→模拟支付→确认收货→评价」。Validates FR-1~FR-24。

**Secondary**

- **SM-3（核心功能全可用）**：发布、搜索、联系（聊天）、订单、评价、退款、管理员后台等核心功能点全部可演示。Validates FR-5~FR-29。
- **SM-4（文档完整）**：文档能独立说明设计、功能与使用方式。Validates 全文档。

**Counter-metrics（不要优化）**

- **SM-C1**：不要为「上架速度」牺牲「审核质量」——审核不能为快而形同虚设，否则「同校可信」失效。Counterbalances SM-1。

## 9. 待决问题

1. 学号认证的具体核实方式：名单校验（自动）还是人工核实？目前按**管理员人工核实**理解（FR-3、FR-28）。
2. 「已完成」状态的触发时机：确认收货后由系统自动标记，还是另有动作？目前按**确认收货后自动标记**（FR-22）。
3. 「封禁」的具体后果：无法登录，还是无法发布/下单？目前按**无法登录/发布**（FR-28）。
4. 成色字段的取值集合：具体枚举值（如「全新 / 九成新 / …」）需确认。
